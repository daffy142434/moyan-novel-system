# 墨研小说系统 · 客户端方案可行性评估

> 评估日期：2026-07-21  
> 评估对象：本地优先桌面客户端 + 轻服务端授权方案  
> 当前状态：**未来备选，不作为当前开发主线**

## 决策更新

当前产品以 Web 网页端为正式主线，项目内容、版本、AI 生成和 Prompt/Skill 运行均由服务端统一处理。本文件仅保留为未来桌面客户端立项时的技术评估，不参与当前 MVP 排期和验收。

建议仅在以下条件之一成立时重新启动客户端立项：

- 用户对离线创作和本地数据控制有明确且持续的强需求；
- 服务端内容存储或 AI 转发成本成为实际经营瓶颈；
- 本地模型成为目标用户的主要使用方式；
- Web 主产品的核心流程、商业化和 Skill 运行协议已经稳定。

## 一、结论

方案技术上可行，综合可行性评估为 **高（约 8/10）**，但当前阶段不建议与 Web 主产品并行开发。

它尤其适合墨研当前阶段：单人创作为主、服务器预算有限、内容文件体积和上下文可能持续增长、核心价值在 Skill 与页面流程，而不是云端协作。

推荐落地形态是：

1. 客户端完成创作流程、Prompt 组装、上下文、模型调用、结构校验、编辑、版本和本地保存；
2. 服务端只保留账号、设备、会员、权益租约、订单、配置下发和更新；
3. P0+ 用 BYOK 让客户端直连模型供应商；
4. P1 增加本地模型；
5. 官方模型代理作为可选增值通道，而不是系统运行的必经路径。

有一个必须接受的边界：如果平台提供自己的模型 API Key，且供应商不支持客户端可用的短期限权令牌，那么请求仍必须经过墨研服务端。共享的长期平台 Key 不能安全地放进客户端。

## 二、分项可行性

| 能力 | 可行性 | 说明 |
|---|---:|---|
| 桌面端复刻原网页页面功能 | 高 | React 页面可以迁入 Tauri，主要变化在数据和系统能力边界 |
| 用户自选目录保存小说 | 高 | 文件选择、目录授权、原子写入、监听和备份均是成熟能力 |
| Skill 驱动客户端页面流程 | 高 | Skill 编译成版本化 Manifest、Prompt 片段和 Schema 即可 |
| 客户端结构化校验模型返回 | 高 | JSON Schema、流式缓存和一次结构修复可本地完成 |
| BYOK 客户端直连模型 | 高 | 可显著降低服务端压力；密钥必须进系统安全凭据库 |
| 本地模型生成 | 中高 | 技术可行，但质量、显存、安装和兼容性取决于用户设备 |
| 服务端只做授权且平台承担模型 Key | 低 | 长期共享 Key 不能放客户端，通常仍需要服务端代理 |
| 客户端会员防破解 | 中 | 租约和签名能提高成本，但客户端永远可能被修改 |
| Prompt 完全保密 | 中低 | 内容发到客户端后可被提取，签名只保护完整性 |
| 云同步与多端协作 | 当前不建议 | 会重新引入存储、冲突、带宽、隐私和服务端压力 |

## 三、主要优势

### 3.1 显著降低服务器资源需求

BYOK 和本地模型模式下，正文、上下文和模型流都不经过墨研服务器。服务端请求以短小的登录、权益续租和配置下载为主，不需要为每次生成维持长连接、生成队列、对象存储和大文本数据库。

这会同时降低：

- 模型推理费用；
- AI 流式转发带宽；
- 长任务并发和队列压力；
- 正文与版本存储空间；
- 数据备份和恢复成本；
- 大量作品内容带来的安全与合规暴露面。

### 3.2 用户数据掌控更强

作品保存在用户选择的普通目录中，可直接查看、复制、用其他编辑器修改和自行备份。即使墨研服务暂时不可用，用户仍能打开和编辑作品，不会因平台故障失去自己的正文。

### 3.3 本地交互更快

项目打开、章节切换、全文搜索、自动保存、版本比较和导出无需经过公网。长篇项目越大，本地读取相比反复从服务器加载越有优势。

### 3.4 服务端更容易扩展

账号、权益和配置请求的资源消耗相对稳定。用户规模增长时，服务端主要扩展无状态 API 和数据库读写，而不是同时扩展生成 Worker、流式连接和内容存储。

### 3.5 商业模式仍然成立

即便用户自行支付模型费用，墨研仍可对软件能力收费：专属创作页面、持续更新的 Skill、结构化生成、审稿、改编、上下文管理、批处理和高级导出。会员不必等同于“平台代付模型 Token”。

## 四、服务器压力对比

| 项目 | 集中式 Web 方案 | 客户端 BYOK/本地模型 | 官方模型代理 |
|---|---:|---:|---:|
| 登录与会员 | 低 | 低 | 低 |
| Prompt/Skill 获取 | 低 | 低，可 CDN 缓存 | 低 |
| 正文存储 | 高且持续增长 | 无 | 可不落库 |
| 版本与备份 | 高且持续增长 | 无 | 无或很低 |
| 上下文上传带宽 | 高 | 无 | 高 |
| 模型流转发带宽 | 高 | 无 | 高 |
| 长任务队列 | 必需 | 不需要 | 可能需要 |
| 模型费用 | 平台承担 | 用户承担或本地计算 | 平台承担后向用户计费 |
| 服务器故障影响 | 无法创作或恢复困难 | 本地编辑不受影响 | 官方生成受影响 |

因此，要真正实现“服务端主要做授权控制”，BYOK 或本地模型必须成为主通道；官方代理只能是可选通道。

## 五、关键风险与处理方式

### 5.1 本地数据丢失

风险：硬盘故障、误删除、系统重装可能造成作品丢失，服务端无法恢复。

处理：首次使用明确提示；提供原子保存、版本快照、回收站删除、项目健康检查、ZIP 备份和定时备份提醒。后续云备份必须是用户主动开启的独立功能。

### 5.2 文件和数据库不同步

风险：用户用外部编辑器改文件，或写文件成功但 SQLite 更新失败。

处理：文件是权威数据，SQLite 是可重建索引；使用哈希、文件监听、恢复日志和冲突确认，不做静默覆盖。

### 5.3 BYOK 使用门槛

风险：普通用户不理解 API Key、计费和模型选择。

处理：设置向导、供应商说明、一键连通测试、推荐模型档位和费用估算。P1 可提供更简单的官方模型套餐，但不要让它成为本地创作的唯一入口。

### 5.4 平台密钥泄露

风险：若把平台 Key 放入安装包，几乎一定会被提取和滥用。

处理：平台 Key 永不下发。使用官方通道时由服务端代理；若供应商支持真正可控的短期令牌，可单独评估直连方案。

### 5.5 Prompt 被提取

风险：Prompt/Skill 配置下发到客户端后，高级用户可以读取。

处理：签名保证完整性，按需切片和混淆提高提取成本；对必须保密的片段只在官方代理服务端使用。不能同时要求完全本地生成和 Prompt 绝对保密。

### 5.6 客户端破解会员

风险：本地二进制可被逆向，单纯本地布尔值不能可靠授权。

处理：服务端签名短期权益租约、设备绑定、周期续租、撤销列表和异常检测。官方代理、支付和重要在线权益始终由服务端再次校验。

### 5.7 本地模型体验不稳定

风险：用户硬件、模型质量、上下文长度和结构化输出能力差异大。

处理：P1 再上线；先支持统一 OpenAI 兼容端点；提供能力检测和最低建议；不把本地模型作为 P0 的唯一真实生成方式。

### 5.8 客户端升级与项目兼容

风险：新版本破坏旧项目或配置包与客户端不兼容。

处理：应用、SQLite、项目和配置包分别版本化；迁移前备份；签名更新；配置声明最低客户端版本；已有项目默认锁定其配置版本。

## 六、对产品和运营的影响

### 6.1 正向影响

- 早期可以用较小服务器支撑更多用户；
- 用户隐私和作品所有权成为产品卖点；
- 服务端故障不会阻断所有本地编辑工作；
- 可以同时服务云模型用户和有本地模型能力的专业用户；
- 后续会员收入可与模型 Token 成本解耦。

### 6.2 必须调整的预期

- 不能把“自动云端备份”作为默认能力宣传；
- 用户换电脑时需要手动迁移项目备份，直到独立云同步上线；
- 客户端退出后，BYOK 生成任务不会像云端 Worker 一样继续运行；
- 客户端下发的 Prompt 不能承诺绝对保密；
- 本地授权不能承诺绝对防破解；
- BYOK 内容虽不经过墨研服务器，仍会发送给用户选定的第三方模型供应商。

---

## 七、建议的首期范围

建议首期严格限制为 Windows 单机、单用户、单实例编辑：

1. 账号登录与设备授权；
2. 本地创作目录和项目恢复；
3. 五章短篇、爽文短剧、AI 漫剧、写手自查和编剧主审页面；
4. Skill 配置包和结构化模型协议；
5. BYOK 直连一个主要供应商和一个 OpenAI 兼容适配器；
6. 本地编辑、版本、外部修改检测和 ZIP 备份；
7. 轻服务端只部署 API、PostgreSQL 和配置/安装包分发。

首期不做云同步、服务端正文、生成队列、多人协作、长篇、媒体处理和复杂运营后台。

---

## 八、最终建议

建议立项，采用开发设计文档中的混合架构，并把以下三条写成不可违反的架构红线：

1. **用户作品默认只存本地，服务端不得悄悄形成正文副本。**
2. **平台长期模型密钥不得进入客户端；低服务器压力依赖 BYOK 或本地模型。**
3. **会员到期或服务器故障不能阻止用户读取和备份自己的本地作品。**

只要接受 BYOK 的使用门槛、Prompt 无法绝对保密以及本地数据需要用户备份这三个现实约束，该方案比原集中式 Web 架构更符合墨研前期资源条件。
